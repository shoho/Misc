## 0. この仕様の狙い

Chromagraph Camera の本質は「フィルターではない」という一点にある。本仕様は、その一点を技術的にどう実現するかを最優先に設計し、UI や周辺機能はそれに従属させる。

### 0.1 「フィルター」と「別のプロセス」の技術的な違い

| | フィルター型（一般的なシネマティック系アプリ） | 別プロセス型（Chromagraph、本仕様） |
|---|---|---|
| 入力 | Apple が処理済みの HEIC/JPEG、または YUV プレビュー | センサーの Bayer RAW（DNG） |
| 信号の状態 | 表示参照（display-referred）。8〜10bit、sRGB/P3 にトーンマップ済み | シーン参照（scene-referred）。12〜14bit リニア、ハイライトの余裕あり |
| 既に失われているもの | クリップしたハイライト、Smart HDR の局所トーンマップの判断、Apple のノイズ処理とシャープニング、Apple のカラーレンダリング | 何も失われていない（デモザイク前） |
| ルックの適用位置 | トーンマップ後に LUT を重ねる | デモザイク直後のシーンリニア段で適用 |
| ハイライトの挙動 | 既にクリップされているので「転び方」を設計できない | ロールオフと彩度の落ち方を自由に設計できる |
| 色の分離 | Apple のカラーレンダリングの上に乗るので二重変換になる | カメラ RGB → XYZ → 作業空間の一段で、ルック側が完全に制御 |

要するに、Apple の処理は「センサー値を画面に出すための Apple の意見（look management）」であり、フィルターはその意見の上に別の意見を重ねる。別プロセス型は Apple の意見を使わず、自分の意見だけで画を作る。

### 0.2 本家の仕様から読み取れる実装のヒント

本表は公開情報からの推定であり、本家の実装を確認したものではない。確度の区分: **公式** = 公式サイト・App Store の記述、**報道** = 取材記事、**利用者報告** = App Store レビュー（バージョン不明）、**推定** = 本仕様の推測。

| 本家の観察事実（確度） | 推定される実装（すべて推定） |
|---|---|
| 解像度が 12MP（4032×3024）止まり。iPhone 17 Pro でも 48MP 不可（利用者報告） | ProRAW ではなく Bayer RAW（ネイティブ RAW）を使っている。ProRAW は Apple の多フレーム合成とノイズ処理を含むため「別プロセス」にならない。Bayer RAW が 12MP に制限されるという情報とも整合する（§2.5） |
| シャープニングがなく、画が眠いという評価（利用者報告、複数） | Apple のシャープニングを通さず、独自の補完も入れていない。設計思想として意図的と推測 |
| 「マルチ露光合成でシャドウがクリーン、ハイライトに余裕」（公式: App Store スクリーンショット） | RAW ブラケット撮影を自前でアライメントして合成している |
| 「ハイライト重視の既定露出」（利用者報告） | 露出バイアスをマイナスに振り、リニア処理で持ち上げる設計 |
| ファインダーにルックが出ない（公式） | フル画質 RAW のデモザイクとルック適用をリアルタイムで行わない。プレビュー YUV に LUT を当てる「フィルター型プレビュー」も、思想に反するので避けている |
| 「シーンリニアな原本を保持」（報道: Yedlin の声明） | DNG そのもの、またはデモザイク済みリニア float を保存 |
| 「ルックの核を保ったまま調整」（公式） | 調整つまみがルックの前段（シーンリニア）とルック内部のパラメータに限定され、ルック後段の自由編集を提供しない |

## 1. システム構成

```
┌─────────────────────────────────────────────────────────────────┐
│ Capture                                                          │
│  AVCaptureSession → AVCapturePhotoOutput                         │
│   ├ 単発: Bayer RAW (DNG)                                        │
│   └ ブラケット: Bayer RAW × 3〜4 (EV -2 / 0 / +1 など)            │
└──────────────┬──────────────────────────────────────────────────┘
               │ DNG + メタデータ
┌──────────────▼──────────────────────────────────────────────────┐
│ Decode                                                           │
│  CIRAWFilter（decoderVersion 固定、無効化可能な処理を無効化）                     │
│   → シーンリニア RGB (float16, 作業色空間)                          │
│  [将来] 自前 Metal デモザイク                                      │
└──────────────┬──────────────────────────────────────────────────┘
               │ scene-linear
┌──────────────▼──────────────────────────────────────────────────┐
│ Merge（ブラケット時のみ）                                          │
│  アライメント（Vision / Metal） → 露出正規化 → 重み付き合成          │
│   → ゴースト除去                                                   │
└──────────────┬──────────────────────────────────────────────────┘
               │ scene-linear HDR
┌──────────────▼──────────────────────────────────────────────────┐
│ Look Pipeline（Metal compute）                                    │
│  1. 前段調整: 露出 / WB / ハレーション（物理的には露光時の現象）       │
│  2. ルック本体: log 変換 → 濃度モデル → 色クロストーク → プリント特性   │
│  3. テクスチャ: グレイン（濃度ドメインで付加）                        │
│  4. ディスプレイ変換: 作業空間 → Display P3 / sRGB, ガマットマップ    │
└──────────────┬──────────────────────────────────────────────────┘
               │ display-referred
┌──────────────▼──────────────────────────────────────────────────┐
│ Gallery / Export                                                  │
│  全 RAW フレーム + manifest + 編集パラメータ JSON（非破壊）                                │
│  HEIC / JPEG 書き出し（ICC プロファイル, EXIF 継承）                │
│  auto-export, Export Size, アーカイブ (zip)                        │
└─────────────────────────────────────────────────────────────────┘
```

設計原則
- **ルックは一箇所にしかない。** プレビュー用の簡易ルック、サムネイル用の別ルックなどを作らない。すべて同じ Look Pipeline を通す。解像度だけを変える。
- **編集はパラメータとして保存し、画像は再現像する。** 原本の DNG は絶対に書き換えない。
- **Apple の意見を混ぜない。** CIRAWFilter を使う場合も、デコーダーのバージョンを固定し、無効化できる処理は明示的に無効化する。無効化できない処理が残ることは前提として認め、検証して明記する（§3.1）。根本対策は自前デモザイク（§3.2）。

## 2. Capture（撮影）

### 2.1 RAW 形式の選択

| 選択肢 | 内容 | 採否 |
|---|---|---|
| Bayer RAW（ネイティブ RAW） | `AVCapturePhotoOutput.availableRawPhotoPixelFormatTypes` の `kCVPixelFormatType_14Bayer_RGGB` 等。デモザイク前のセンサー値。実出力は 12MP。Quad Bayer 機でも Bayer RAW はビニング後の出力であり、48MP の Bayer RAW が third-party に提供されているかは未確認（§2.5） | **採用**。これが「別プロセス」の前提 |
| Apple ProRAW | リニア RGB の DNG。Apple の多フレーム合成、ノイズ処理、デモザイクを経ている。48MP 可 | 不採用（コア）。48MP が必要なら「高解像度モード（Apple 現像ベース）」として処理前提の異なる別モードを定義する（§2.5）。既定では提供しない |
| HEIF/JPEG | Apple 処理済み | 不採用 |

実装
```swift
let output = AVCapturePhotoOutput()
output.isAppleProRAWEnabled = false
guard let rawFormat = output.availableRawPhotoPixelFormatTypes.first(where: {
    AVCapturePhotoOutput.isBayerRAWPixelFormat($0)
}) else { /* 非対応機種 */ }

let settings = AVCapturePhotoSettings(rawPixelFormatType: rawFormat,
                                      processedFormat: nil)   // 処理済み画像は要求しない
settings.photoQualityPrioritization = .quality
// maxPhotoDimensions は §2.5 の実機確認で記録した値に従う。v1 は 12MP 固定
```

備考
- `processedFormat: nil` にすると Apple 処理済みのサムネイルすら生成されない。ギャラリーのサムネイルは自前パイプラインで作る（原則通り）。
- 48MP の Bayer RAW については断定しない。Apple の WWDC26 Camera and Photo Technologies Group Lab では、Quad Bayer センサーの Bayer RAW 出力は画素をまとめた出力で、フル解像度の Quad Bayer RAW は未提供と説明されている（レビュー指摘 #5）。一方で Halide が 48MP の非 ProRAW RAW を謳っているとする記事もあり、Apple Developer Forums には `maxPhotoDimensions` を上げても 12MP の Bayer RAW しか返らないという報告がある。情報が食い違うため、§2.5 の実機確認で判定する。本家が 12MP 止まりである事実（§0.2）は「取得できない」側と整合する。

### 2.2 露出制御（ハイライト重視）

ルックがシーンリニアで動くので、ハイライトを飛ばさないことが最優先。シャドウはリニア処理で持ち上げられるが、クリップしたハイライトは戻らない。

- 既定: `exposureTargetBias = -1.0 EV`（機種とシーンで -0.7〜-1.5 の範囲を調整）
- 測光: `exposureMode = .continuousAutoExposure` のまま、`exposurePointOfInterest` を使わずバイアスで制御する。ユーザーには EV ダイヤルを提供（±2 EV）。
- 将来: プレビュー YUV のヒストグラムからハイライトクリップ率を監視し、バイアスを動的に決める「ハイライト優先 AE」。

### 2.3 マルチ露光（ブラケット撮影）

```swift
let brackets = [-2.0, 0.0, +1.0].map {
    AVCaptureAutoExposureBracketedStillImageSettings
        .autoExposureSettings(exposureTargetBias: Float($0))
}
let settings = AVCapturePhotoBracketSettings(rawPixelFormatType: rawFormat,
                                             processedFormat: nil,
                                             bracketedSettings: brackets)
settings.isLensStabilizationEnabled = output.isLensStabilizationDuringBracketedCaptureSupported
```

- `output.maxBracketedCapturePhotoCount` を確認（多くの機種で 3〜4）。
- 露出差はシャッター速度で付ける（ISO 固定）方がノイズモデルが単純になる。`AVCaptureManualExposureBracketedStillImageSettings` で duration を変える方式も検討。
- 静止シーン判定: プレビューのフレーム差分が小さいときだけブラケット、動体が多いときは単発に自動で落とす。

### 2.4 その他のカメラ機能

| 機能 | 実装 |
|---|---|
| レンズ切替 | `AVCaptureDevice.DiscoverySession` で 0.5x / 1x / 2x(3x/5x) を列挙。仮想デバイス（`builtInTripleCamera`）は自動切替が Apple 側で起きるため使わず、物理デバイスを個別に選ぶ |
| 既定レンズ | Preferences に保存 |
| マクロ | 超広角の自動マクロ切替は仮想デバイスの機能なので、物理デバイス選択なら自然に無効。有効にしたい場合のみ仮想デバイスへ |
| 前面カメラ | 対応。ミラーモードはギャラリー表示と書き出しで水平反転 |
| モノクロ | 撮影前にフラグを立て、ルックの「モノクロ変種」を適用。RAW はカラーで保存するので後から戻せる（本家は編集時に戻せないという利用者報告があるが未確認。§12） |
| プレビュー | `AVCaptureVideoPreviewLayer` をそのまま表示。ルックは当てない。露出のオーバー/アンダーを示すゼブラのみオーバーレイで提供（これは画像処理ではなく測定なので思想に反しない） |

### 2.5 高解像度（48MP）の扱いと実機確認

方針
- v1 は 12MP 固定。48MP は実装範囲に含めない。
- 48MP の採否は、下記の実機確認で「Bayer RAW として 48MP が取得できる機種」が確認できた場合に限り、その機種向けの「高解像度 Bayer モード」として検討する。
- Bayer RAW で取得できない場合、48MP は ProRAW でのみ可能である。ProRAW は Apple の多フレーム合成・ノイズ処理・デモザイクを経たリニア RGB であり、「別プロセス」の前提を満たさない。提供するなら「高解像度モード（Apple 現像ベース）」として、UI・パイプライン・保存データ（`manifest.json` の `source.kind = "proraw"`）のすべてで通常モードと区別し、Decode 段が異なることを明示する。Look Pipeline（§5）は共通で使えるが、入力の性質（ノイズ、シャープネス、ハイライトの既処理）が異なるため、ルックの検証は別に行う。
- 対応機種として保証するのは、実機確認表に記録のある組み合わせだけとする。

実機確認の手順
1. 対象機種ごとに、各物理カメラ（wide / ultraWide / telephoto / front）で以下を総当たりする: `isAppleProRAWEnabled` の on/off、`availableRawPhotoPixelFormatTypes` の各形式、`maxPhotoDimensions`（`AVCapturePhotoOutput` と `AVCapturePhotoSettings` の両方）の既定値と最大値、`photoQualityPrioritization` の `.speed` / `.balanced` / `.quality`。
2. 生成された DNG を読み、実寸（`ImageWidth` × `ImageLength`）、`PhotometricInterpretation`（CFA か LinearRaw か）、`BitsPerSample`、`CFAPattern` を記録する。
3. 記録フォーマット:

| 機種 | iOS | カメラ | ProRAW | RAW 形式 | maxPhotoDimensions 指定 | quality | 実出力寸法 | Photometric | 備考 |
|---|---|---|---|---|---|---|---|---|---|
| （実機で記入） | | | | | | | | | |

4. 「48MP かつ CFA」の行が得られた機種のみ、高解像度 Bayer モードの候補とする。それ以外の機種では 48MP を約束しない。

## 3. Decode（RAW 現像の前半）

### 3.1 v1: CIRAWFilter をできる限り「素」で使う

自前デモザイクは工数が大きいので、v1 は Core Image の `CIRAWFilter` を使う。ただし、各パラメータを 0 にしても Apple 由来の処理をすべて切れるわけではない。レビュー指摘（#6）によれば、RAW 9 デコーダーでは色ノイズ処理が CoreML モデルで自動的に行われるため `colorNoiseReductionAmount` は効果を持たず、`detailAmount` と `moireReductionAmount` も RAW 9 ではサポートされない。また `CIRAWFilter` は既定で、その画像種別に対して利用可能な最新のデコーダーを選ぶため、OS 更新で同じ原本・同じ設定でも現像結果が変わりうる。

本仕様は「全処理を切る」とは主張しない。方針は次の 3 点である。

1. **デコーダーを固定する。** `supportedDecoderVersions` を確認し、仕様で定めた固定バージョン `pinnedDecoderVersion` を `decoderVersion` に設定する。固定バージョンは実機検証（後述）で決め、以後アプリの意図的なリリースでのみ変更する。第一候補は RAW 8 系（CoreML による自動処理が入る前の世代）。`CIRAWDecoderVersion` の実際の列挙値は SDK で確認する。
2. **固定バージョンが使えない場合の挙動を定める。** `supportedDecoderVersions` に固定バージョンがない場合は、利用可能なもののうち固定バージョンに最も近い（古い側を優先）バージョンを使う。実際に使った版を `manifest.json` の `decoder.usedVersion` に記録し、`requestedVersion` と異なる写真には UI で「現像エンジンが変わったため、当時と同一の見た目は保証されない」と表示する。自動で最新版へ上げない。
3. **無効化できる処理と残る処理を検証で確定し、表に残す。** 下の対応表を実機検証で埋める。

```swift
let raw = CIRAWFilter(imageData: dngData, identifierHint: "com.adobe.raw-image")!
let pinned = CIRAWDecoderVersion.version8   // 仕様で固定。実機検証で確定
raw.decoderVersion = raw.supportedDecoderVersions.contains(pinned)
                   ? pinned
                   : nearestSupported(to: pinned, in: raw.supportedDecoderVersions)   // 記録と警告は呼び出し側で
raw.isDraftModeEnabled       = false
raw.baselineExposure         = 0
raw.exposure                 = 0
raw.boostAmount              = 0      // Apple のグローバルトーンカーブ
raw.boostShadowAmount        = 0
raw.localToneMapAmount       = 0      // ローカルトーンマップ
raw.extendedDynamicRangeAmount = 0
raw.contrastAmount           = 0
raw.detailAmount             = 0      // RAW 9 では非サポートと指摘あり（要検証）
raw.sharpnessAmount          = 0
raw.luminanceNoiseReductionAmount = 0
raw.colorNoiseReductionAmount     = 0 // RAW 9 では効果なしと指摘あり（要検証）
raw.moireReductionAmount     = 0      // RAW 9 では非サポートと指摘あり（要検証）
raw.neutralTemperature / neutralTint = DNG の AsShotNeutral から
raw.colorSpace               = CGColorSpace(name: CGColorSpace.extendedLinearDisplayP3)
```

デコーダー別の対応表（実機検証で埋める。記入前の値はすべて「要検証」）

| 設定 | 目的 | RAW 8 | RAW 9 | 備考 |
|---|---|---|---|---|
| `boostAmount = 0` | グローバルトーンカーブを切る | 要検証 | 要検証 | |
| `localToneMapAmount = 0` | ローカルトーンマップを切る | 要検証 | 要検証 | |
| `luminanceNoiseReductionAmount = 0` | 輝度 NR を切る | 要検証 | 要検証 | |
| `colorNoiseReductionAmount = 0` | 色 NR を切る | 要検証 | 効果なし（指摘 #6） | RAW 9 では CoreML が自動処理 |
| `detailAmount = 0` / `sharpnessAmount = 0` | シャープニングを切る | 要検証 | detail は非サポート（指摘 #6） | |
| `moireReductionAmount = 0` | モアレ処理を切る | 要検証 | 非サポート（指摘 #6） | |
| デモザイク | 切れない | 常に Apple | 常に Apple | v2 で自前に置換 |
| レンズ補正 | 切れるか不明 | 要検証 | 要検証 | |

- `linearSpaceFilter` プロパティに CIFilter を差し込むと、デモザイク直後のリニア段で処理できる。ハレーションの付加はここが物理的に正しい位置。
- 出力はリニア float16 の `CIImage` → `MTLTexture` へ。以降は Metal で処理。

検証（固定バージョンの決定と、残る処理の把握のために行う）

| 検証 | 方法 | 判定 |
|---|---|---|
| グレースケールの線形性 | 反射率既知のグレーチャート（6 段以上）を撮影し、出力リニア値を反射率に対して回帰 | 決定係数 R² > 0.999、残差 < 1%。トーンカーブが残っていれば非線形になる |
| 暗部ノイズ | 低照度の均一面を撮影し、ノイズの分散と空間自己相関を測る | NR が効いていれば隣接画素に正の相関が出る。相関係数 < 0.05 を「NR なし」とみなす |
| 飽和色 | 高彩度パッチ（カラーチャート、LED 光源）を撮影し、作業空間で色相の回転とクリップを確認 | 色相角の変化 < 2°。クリップは記録する |
| OS 更新前後 | 同一 DNG を更新前後で現像し、差分を測る | ΔE2000 平均 < 0.5、最大 < 2.0。超えたらデコーダー固定が破られたと判断し、`usedVersion` の記録を確認する |
| デコーダー間差 | 同一 DNG を RAW 8 と RAW 9 で現像して比較 | 対応表の根拠として差分画像を保存する |

限界
- デモザイクは Apple のアルゴリズム。補間の癖（偽色、ジッパー）は Apple 由来になる。
- デコーダーを固定しても、Apple が将来そのバージョンを `supportedDecoderVersions` から外す可能性がある。その場合は上記 2 の挙動になり、再現性は「近似」に落ちる。再現性を完全にするには v2 の自前デモザイク（§3.2）が必要で、これが根本対策である。

### 3.2 v2: 自前デモザイク（Metal）

- DNG を ImageIO ではなく自前パーサで読む（TIFF/EP 準拠。`CFA Pattern`, `BlackLevel`, `WhiteLevel`, `ColorMatrix1/2`, `AsShotNeutral`, `CalibrationIlluminant`）。
- Metal compute で: 黒レベル減算 → ホワイトレベル正規化 → WB ゲイン → デモザイク（AHD または Malvar-He-Cutler。後者は 5×5 カーネルで高速）→ カメラ RGB → XYZ（ColorMatrix の逆行列、2つのイルミナント間を色温度で補間）→ 作業空間。
- レンズ補正（周辺減光、歪曲）は DNG の OpcodeList を解釈するか、機種別テーブルを持つ。

### 3.3 作業色空間

- **リニア、広色域、float16。** 候補は ACEScg（AP1）または Linear Rec.2020。iOS の表示が Display P3 なので、Linear P3 でも実用上は足りるが、ルック設計で飽和色の挙動を扱うために AP1 を推奨。
- 作業空間での値 1.0 = 18% グレーの約 5.5 倍（ディフューズ白）となるよう露出を正規化する。つまり 18% グレー = 0.18。ルックの入力はこの基準で設計する。
- 演算は float32、テクスチャ保存は float16。float16 の正規化数の下限（約 6.1e-5）より小さい値は精度を失うため、§5.2 の下限オフセットはこれより大きく取る。カメラ行列の変換で生じる負値や NaN の扱いは §5.2 で定義する。

## 4. Merge（マルチ露光合成）

v1 では単発撮影のみ。v2 で実装。

1. **アライメント**: 各フレームを 1/4 に縮小したリニア輝度で `VNHomographicImageRegistrationRequest` を実行し、ホモグラフィを得る。手持ちの微動には十分。動体はここでは扱わない。
2. **露出正規化**: 各フレームの値に 2^(-EV) を掛け、同一の放射輝度スケールに揃える。
3. **有効画素の判定（動体判定より先に行う）**: 各フレーム・各画素について、いずれかのチャンネルの RAW 値がホワイトレベルの 95% 以上なら「飽和」、正規化前の値がノイズ床（黒レベル付近の標準偏差 σ0）の 3 倍未満なら「暗部」とし、どちらも「無効」とする。
4. **重み付き合成**: 有効画素だけを使う。重みは推定 SNR に比例させる。ショットノイズ支配を仮定すると、正規化前の信号値 s に対して σ(s) = sqrt(g·s + σ0²)（g はゲイン）なので、w = s / σ(s)。全フレームで無効な画素は、飽和なら最も短い露出の値、暗部なら最も長い露出の値をそのまま使う。
5. **動体判定**: 基準フレームは EV 0。ただし基準フレームが無効な画素では、その画素が有効なフレームのうち EV 0 に最も近いものを「代替基準」とする。残差は、比較する 2 フレームの両方で有効な画素についてのみ計算し、露出正規化後の差を両フレームのノイズ推定から求めた σ で割って正規化する。|Δ| / σ > τ（τ = 4 を初期値）の画素を候補とし、5×5 近傍の多数決で動体と確定する。動体画素は代替基準フレームの値を単独で使い、他フレームを混ぜない。
6. 結果はシーンリニア HDR として Look Pipeline へ。ハイライトの余裕が約 2 EV 広がる。

設計上の注意
- 合成は必ずリニア空間で行う。ログや表示空間で合成するとルックの前提が崩れる。
- **飽和画素を動体と誤判定しない。** 静止シーンで、基準フレームが飽和（値 1.0）、EV -2 フレームから復元した値が 2.0 の画素に対し、基準フレームとの残差判定を素朴に行うと差 1.0 が「動体」と判定され、復元したハイライトが基準の飽和値に戻される。有効画素の判定を動体判定より先に行い、無効画素を残差計算から外すことでこれを避ける（レビュー指摘 #8）。
- 閾値 τ を大きくするだけでは、ハイライトの復元と動体検出を両立できない。ノイズで正規化した残差と有効画素マスクの組み合わせが必要。
- 合成後のノイズ特性は単発と変わるので、グレインのパラメータは合成の有無で切り替える。

評価条件（静止シーンの白飛び復元と、動体のゴーストは別々に評価する）

| 条件 | 期待結果 | 判定 |
|---|---|---|
| (a) 静止シーン、ハイライトに飽和領域あり | 飽和領域が EV -2 フレームから復元され、基準の飽和値に戻らない | 復元された放射輝度の誤差 < 5%（既知輝度の光源で測る） |
| (b) ハイライト付近を横切る動体（窓の前を歩く人など） | ゴーストが出ず、かつ窓のハイライトは復元される | 目視でゴーストなし、ハイライト領域が (a) の判定を満たす |
| (c) 暗部の動体と暗部ノイズ | ノイズを動体と誤判定しない | 静止した暗部での誤判定率 < 1% |
| (d) 全フレームで飽和する光源 | 最短露出の値で埋まり、穴や NaN が出ない | 出力が有限で単調 |

## 5. Look Pipeline（ルック本体）

ここが本アプリの価値のすべてである。

### 5.0 位置づけと製品目標

一次情報で確認できること（Yedlin「On Color Science」ほか公開資料）
- Yedlin の手法は、実測データに基づいて 3 次元の色空間全体を扱う変換を構築し、散在データの補間で display prep を作るもので、粒状感も実測した確率分布から再現する、と説明されている。
- 資料は手順の詳細を意図的に避けており、具体的な関数形や行列は公開されていない。Chromagraph の内部実装も非公開である。

本仕様の濃度モデルの位置づけ（独自提案）
- 本節の S 字特性曲線、濃度ドメインの 3×3 クロストーク、プリント特性は、「フィルムの濃度の振る舞いを模した独自ルック」を設計するための**候補モデル**である。Yedlin の方式や Chromagraph の実装と同じである根拠はなく、本仕様はそれを主張しない（レビュー指摘 #11）。
- 一次情報と共通する方針は「シーンリニアから表示までを一つの display prep として一括設計する」ことだけである。

製品目標
- 本プロジェクトの目標は、「別プロセス」という構造を踏襲した**独自ルック**であり、Chromagraph の出力の再現ではない。M0（§11）の完了条件はこの目標に対応する。
- 本家への近似を目標に加える場合は、同一機種・同一シーン・同一露出で本家と本アプリを撮り比べ、ΔE2000 と目視 A/B で評価する手順を別に定義し、M0 とは別のマイルストーンとして扱う。独自ルックの試作が終わっても、本家との近似が確認されたことにはならない。

本節の各主張の区分: 「一次情報」= Yedlin の公開資料で確認できる、「推定」= 公開情報からの推測、「独自提案」= 本仕様の設計案。特記のない技術記述はすべて独自提案である。

本仕様では、このモデルをパラメトリックに設計し、実行時は 3D LUT に焼いて高速化する。

### 5.1 全体の段構成

```
scene-linear (AP1)
  │
  ├─ [A] 前段調整（ユーザーのつまみ: 露出, WB, ハレーション）
  │
  ├─ [B] log エンコード（シーンリニア → 対数露光量）
  │
  ├─ [C] 濃度モデル（フィルムのネガ特性: 各層の S 字特性曲線）
  │
  ├─ [D] 色クロストーク（減法混色の層間干渉: 濃度ドメインの 3×3 + 非線形）
  │
  ├─ [E] プリント特性（ネガ → ポジの S 字, 黒の締まりと白のロールオフ）
  │
  ├─ [F] グレイン（濃度ドメインで付加）
  │
  ├─ [G] 出力変換（濃度 → 透過率 → リニア → Display P3 ガンマ, ガマットマップ）
  │
display-referred
```

各段の入出力（レビュー指摘 #7 を受けて明示）

| 段 | 入力 | 出力 | 実行形態 |
|---|---|---|---|
| [A] | scene-linear（AP1、18% グレー = 0.18。演算 float32、保存 float16） | 同じ空間のリニア値 | 行列演算 + ハレーション（シェーダー） |
| [B] | scene-linear | 正規化 log 値 t ∈ [0, 1]（§5.2） | シェーダーで直接計算（または 1D シェーパー LUT） |
| [C] | t | ネガ濃度 D（各層、Dmin〜Dmax） | LUT-A に含める |
| [D] | D | D'（クロストーク後の濃度） | LUT-A に含める |
| [E] | D' | プリント濃度 Dp（Dp_min〜Dp_max、範囲 [0, 4] にクランプ） | LUT-A に含める |
| [F] | Dp | Dp + n（濃度ドメインでノイズを加算） | シェーダー（LUT の外） |
| [G] | Dp + n | display-referred（Display P3、OETF 適用後、[0, 1]） | シェーダーで解析的に計算、または濃度入力の LUT-B（33³） |

- **LUT-A** = [C]→[D]→[E]。3D LUT（65³、float16）。入力はシェーパー後の t、出力はプリント濃度 Dp。つまみ操作で再焼成する。
- **[F] グレイン** は LUT-A の出力（濃度）に加算する。表示空間に加えると濃度依存の強度制御が成立しないため、LUT-A と [G] の間に置くことを固定する（§6.2）。
- **[G]** は濃度を入力とする純粋な関数（10^-D → 行列 → ガマットマップ → OETF）。つまみに依存しないので再焼成は不要。解析的に計算するのが既定で、LUT-B は性能上必要な場合のみ。
- 実行時の順序は「[A] 行列 → ハレーション → [B] シェーパー → LUT-A → [F] グレイン → [G] 出力変換」で固定し、本節の段構成、§6.2、§9 の参照実装をすべてこの順序に揃える。

### 5.2 [B] log エンコード

入力はシーンリニア値 L（AP1、各チャンネル独立、18% グレー = 0.18）。ゼロ・負値・範囲外の扱いを含めて次のように定義する（レビュー指摘 #9）。

```
// 前処理
if !isfinite(L) { L = 0 }            // NaN / ±Inf は 0 として扱う
L = max(L, 0)                        // 負値は 0 にクランプ

// log 変換（stops 単位、下限オフセット付き）
a = 0.18 * 2^-10                     // ≈ 1.758e-4。L = 0 のとき x = -10
x = log2((L + a) / 0.18)             // 18% グレーで x ≈ 0（正確には log2(1 + 2^-10) ≈ 0.0014）

// LUT 座標への正規化
x_min = -10, x_max = +10             // 20 stops
t = clamp((x - x_min) / (x_max - x_min), 0, 1)
```

定数の根拠
- 下限オフセット a は、L = 0 を「18% グレーの 10 stops 下」に割り当てる。iPhone のセンサーのダイナミックレンジ（10〜11 stops）より下はノイズなので、これ以上の暗部分解能は不要。a は float16 の正規化数の下限（約 6.1e-5）より大きく、float16 保存でも精度を失わない。
- 上限 x_max = +10 は L ≈ 184（ディフューズ白の約 184 倍）。ブラケット合成で得られるハイライトの余裕（+2〜3 EV）はこの内側に収まる。これが入力段で起きる唯一のクリップであり、HDR の 1 を超える値はクリップしない。
- 負値のクランプは、カメラ行列の変換で生じる微小な負値（作業空間の外側の色）を 0 にする。暗部の飽和色で色相がわずかに動くが、AP1 を選ぶことで負値の発生自体を減らしている。
- 65³ の LUT-A では節点間隔が 20/64 = 0.3125 stops。四面体補間で滑らかな曲線なら十分。

期待値（Python と Metal の両方でこの表を単体テストにする）

| L | x | t |
|---|---|---|
| NaN, +Inf | 0 として扱う | 0 |
| -0.01 | 0 として扱う | 0 |
| 0 | -10.000 | 0 |
| 1e-6 | -9.992 | 0.0004 |
| 1e-4 | -9.351 | 0.0325 |
| 0.18 | 0.0014 | 0.5001 |
| 1.0 | 2.474 | 0.6237 |
| 5.5 | 4.934 | 0.7467 |
| 184.32 | 10.000 | 1.0 |
| 1e4 | 15.76（クランプ） | 1.0 |

- 定数（0.18、a、x_min、x_max）は `shaper.json` として Python とアプリで共有し、別々に書かない。
- 3D LUT の入力を log にすることで、暗部の分解能を確保する。1D シェーパー LUT にする場合も同じ式から生成する。
- [G] に渡す濃度は [0, 4] にクランプし、10^-D が 1e-4 以上になるようにする。これも Python と Metal で同じ境界にする。

### 5.3 [C] 濃度モデル（ネガ）

フィルムの特性曲線 D(logE) を各層（R/G/B に対応する C/M/Y 染料）に持つ。パラメトリックには次の形が扱いやすい。

```
D(x) = Dmin + (Dmax - Dmin) / (1 + exp(-k * (x - x0)))^a
```

- Dmin: ベース濃度（黒の持ち上がり）
- Dmax: 最大濃度
- k: 直線部の傾き（ガンマ）
- x0: 中点（感度）
- a: 肩の非対称性（ハイライトのロールオフの緩やかさ）

層ごとに k, x0, a を微妙に変えることで、ハイライトの色の転び（例: 白に向かって暖色に抜ける）や暗部の色（例: 青緑に沈む）が生まれる。この層ごとの差が、本モデルでフィルム的な色の転びを作る主な自由度である（独自提案。Yedlin の方式との対応は不明）。数値は参照画像を見ながら決める（§9 参照）。

### 5.4 [D] 色クロストーク

実際のフィルムでは、ある層の露光が隣接層の濃度にも影響する（インターイメージ効果）。濃度ドメインで次のように扱う。

```
D' = M · D + f(D)
```

- M: 3×3 行列。対角が 1、非対角が小さな負または正の値。彩度と色相のねじれを作る。
- f: 非線形項。濃度が高い（暗い）ほど彩度が落ちる、などの挙動。

本モデルでは、この段があるかどうかが「単純な 1D トーンカーブ + 彩度調整」と「フィルムのように振る舞う」の分かれ目になる（独自提案）。RGB 空間で彩度を上げ下げするのとは質的に違い、色相ごとに異なる飽和の仕方が出る。

### 5.5 [E] プリント特性

ネガ濃度をもう一度 S 字に通してポジにする。ここで最終的なコントラスト、黒の締まり、白の抜けが決まる。

- 黒は完全な 0 にしない（プリントの Dmin）。
- 白は 1.0 に漸近し、クリップしない。どんなに明るい入力でも滑らかに飽和する。

### 5.6 [G] 出力変換とガマットマップ

- 濃度 → 透過率（10^-D）→ 作業空間リニア → Display P3。
- AP1 の飽和色は P3 の外に出るので、ガマットマップが必要。輝度を保って彩度を落とす方式（色相保持）を使い、チャンネルクリップはしない。チャンネルクリップは色相が回るので、フィルム的な「白に抜ける」挙動と相性が悪い。
- 書き出し先が sRGB の場合は同様に P3 → sRGB のガマットマップ。

### 5.7 ユーザー調整（「ルックを失わずに調整」の実装）

つまみは [A] の前段と、[C]〜[E] のパラメータの**限定的な**変更に閉じる。ルック後段（表示参照）での自由編集は提供しない。これにより、どう動かしても「このアプリの画」から外れない。

| つまみ | 作用する段 | 実装 |
|---|---|---|
| 露出 | [A] | リニアに 2^EV を掛ける。ルックに入る前なので、ハイライトのロールオフの位置が自然に動く |
| ホワイトバランス（色温度 / ティント） | [A] | リニアで Bradford 変換。ルックの色の転びは保たれる |
| コントラスト | [C][E] | k を ±20% の範囲でスケール。中点 x0 は固定 |
| トーン（シャドウ / ハイライト） | [C] | Dmin, Dmax と a の微調整。曲線の形は崩さない |
| カラー（彩度 / 色のねじれ） | [D] | M の非対角成分を 0〜1.5 倍でスケール。0 にしても完全なニュートラルにはならない（f の項が残る） |
| テクスチャ（グレイン量 / 粒子サイズ） | [F] | 後述 |
| ハレーション量 | [A] | 後述 |
| モノクロ | [D] | 濃度を輝度の重みで単層に畳む。パンクロ的な重み（R 寄り）を既定に |

つまみを動かすたびに LUT-A（[C]〜[E]）を再焼成する。[G] はつまみに依存しないので再焼成しない。65³ = 274,625 点の評価は Metal compute で 1ms 未満。

## 6. テクスチャ

### 6.1 ハレーション

物理的には、強い光がフィルムベースを抜けて裏面で反射し、再び感光層に戻る現象。赤感光層が最も裏側にあるため赤〜橙に色づく。

実装（[A] の段、シーンリニアで）
1. 作業空間リニアから、閾値（例: ディフューズ白の 2 倍）以上の成分を抽出。
2. ガウシアンピラミッドで広い半径（画像幅の 2〜5%）にブラー。2〜3 段の異なる半径を合成すると裾が自然になる。
3. 赤 > 緑 > 青 の重み（例: 1.0 / 0.35 / 0.1）で色づけ。
4. 元画像に加算。加算なのでハイライトの周囲が「持ち上がる」。
5. ユーザーの「ハレーション量」は 3 のゲインに掛ける。

ルックの前段で加算するので、ハレーションそのものもルックのロールオフとクロストークを通る。これが「後がけのグロー」と見え方が違う理由。

### 6.2 グレイン

実装（[F] の段、濃度ドメインで）
1. 濃度が中間（D ≈ 0.6〜1.2）で最も強く、Dmin と Dmax 付近で弱くなる重み関数を持つ。実フィルムの RMS 粒状度の濃度依存性に合わせる。
2. ノイズは層ごとに無相関（R/G/B 別々の乱数）。これが色のついたグレインになる。青層はやや強め。
3. 粒子サイズは**出力解像度ではなくセンサー解像度基準**で決め、書き出しサイズを変えても粒の見え方が相対的に同じになるようにする。
4. 生成はブルーノイズのタイルを、画像ごとに異なるオフセットでサンプリング。ガウシアンの白色ノイズは「デジタルノイズ」に見えるので使わない。粒の「塊感」は低周波ノイズを軽く混ぜて作る。
5. ユーザーの「グレイン量」は振幅、「粒子サイズ」はタイルのサンプリング倍率。

処理順序（レビュー指摘 #7）
- グレインは LUT-A の出力であるプリント濃度 Dp に加算し、その後に [G] の出力変換を通す。順序は「LUT-A → [F] → [G]」で固定。
- [G] の後（表示空間）に加えると、同じノイズ量でも結果が変わり、濃度依存の強度制御が成立しない。例: 濃度 D = 1 にノイズ 0.1 を足してから透過率に変換すると 10^-(1.1) ≈ 0.0794、変換後に 0.1 を足すと 10^-1 + 0.1 = 0.2 で、同じ値にならない。
- 加算後の濃度は [0, 4] にクランプしてから [G] に渡す。

検証
- Python の参照実装と Metal の LUT 版を、同じシードと同じブルーノイズタイルで実行し、(1) [F] 直前の濃度、(2) [F] 直後の濃度、(3) 最終出力、の 3 点で一致を確認する（許容誤差 1/1024）。
- 濃度依存の重み関数は、均一なグレーのパッチを 10 段の明るさで現像し、各段の粒の RMS が設計した重み関数と一致することで確認する。

## 7. Gallery / Export

### 7.1 データモデル

原本・編集・キャッシュを分け、ブラケットの全フレームを原本として保持する（レビュー指摘 #10）。

```
Library/
  <uuid>/
    manifest.json         # 撮影記録。不変
    frames/
      f00.dng             # センサー RAW。不変。単発なら 1 枚、ブラケットなら全フレーム
      f01.dng
      f02.dng
    edits.json            # 編集パラメータ。可変。バージョン付き
    cache/                # 再生成可能。容量逼迫時に削除してよい
      merged.exr          # 合成後のシーンリニア（v2）
      thumb.heic          # サムネイル（ルック適用済み）
      render.json         # 直近レンダリングの条件とハッシュ（再現性検証用）
```

`manifest.json`（撮影時に書き、以後変更しない）
```json
{
  "schema": 1,
  "capturedAt": "2026-11-03T12:00:00+09:00",
  "device": { "model": "iPhone16,1", "os": "17.5", "camera": "builtInWideAngleCamera" },
  "source": { "kind": "bayer", "pixelFormat": "RGGB14", "dimensions": [4032, 3024] },
  "frames": [
    { "id": "f00", "file": "frames/f00.dng", "exposureBias": -2.0, "shutter": 0.004, "iso": 100 },
    { "id": "f01", "file": "frames/f01.dng", "exposureBias":  0.0, "shutter": 0.016, "iso": 100 },
    { "id": "f02", "file": "frames/f02.dng", "exposureBias":  1.0, "shutter": 0.033, "iso": 100 }
  ],
  "referenceFrame": "f01",
  "merge": { "enabled": true, "version": "merge-1", "params": { "tau": 4.0, "saturation": 0.95 } },
  "decoder": { "engine": "CIRAWFilter", "requestedVersion": "RAW8", "usedVersion": "RAW8" }
}
```

`edits.json`
```json
{
  "schema": 1,
  "lookVersion": "2026.11",
  "pipelineVersion": "pipe-1",
  "exposure": -0.3,
  "whiteBalance": { "temperature": 5200, "tint": 2 },
  "contrast": 1.0,
  "tone": { "shadows": 0, "highlights": 0 },
  "color": { "crosstalk": 1.0 },
  "texture": { "grain": 1.0, "grainSize": 1.0, "halation": 1.0 },
  "monochrome": false,
  "crop": { "rect": [0,0,1,1], "rotation": 0, "flipH": false, "flipV": false }
}
```

規則
- `manifest.json` と `frames/` は不変の原本。ブラケット撮影では全フレームを保存し、基準フレームと各フレームの実露出（シャッター、ISO、バイアス）を記録する。`cache/` を全部消しても、`frames/` + `manifest.json` から同じ合成を再実行できる。
- `merged.exr` は再生成可能なキャッシュであり、原本ではない。合成の再現性は `merge.version` と `merge.params` で担保する。
- `source.kind` は `bayer` を既定とし、§2.5 の高解像度モードを採用した場合のみ `proraw` を取る。両者は Decode 段が異なるため、同じ `lookVersion` でも「同じ処理」とは扱わない。
- 原本は iOS の写真ライブラリには保存しない（本家と同じ）。ライブラリへ入れるのは書き出し結果のみ。

ルックの再現性
- `lookVersion` は識別子であり、それだけでは当時の画を再現できない。アプリは **ルックレジストリ** `Looks/<lookVersion>/look.json`（[C]〜[G] の全パラメータ）を同梱し、各 `lookVersion` が依存する `pipelineVersion`（段構成とシェーダーのコードの版）を `look.json` に記録する。過去の `lookVersion` と `pipelineVersion` のコードは削除せず、アプリに残し続ける。
- 当時の画を「同一」として再現できる条件は、(1) 同じ `lookVersion` のパラメータ、(2) 同じ `pipelineVersion` のコード、(3) 同じ `decoder.usedVersion`、(4) 同じ `merge.version`、の 4 つがすべて揃うこと。一つでも欠ける場合は「近似」であり、UI でその旨を表示する。「同一」と表示してよいのは 4 条件が揃うときだけ。
- `cache/render.json` には、直近レンダリングに使った上記 4 条件と出力のハッシュ（SHA-256）を記録し、再現性検証の比較対象にする。

### 7.2 表示

- ギャラリーのサムネイルと全画面表示は、同じ Look Pipeline を解像度だけ変えて走らせる。全画面は 1/2 解像度で即時表示し、バックグラウンドでフル解像度に差し替える。
- 編集中のプレビューは 1/4 解像度で 3D LUT 再焼成とレンダリングを行い、60fps を目標にする。

### 7.3 書き出し

| 項目 | 仕様 |
|---|---|
| 形式 | HEIC（既定）/ JPEG |
| 色空間 | Display P3（ICC 埋め込み）。sRGB も選択可 |
| ビット深度 | HEIC は 10bit を選択可能に（グレインとロールオフのバンディング回避） |
| サイズ | フル / 大（長辺 3000）/ 中（長辺 2000）/ 小（長辺 1200） |
| メタデータ | DNG の EXIF（撮影日時、レンズ、露出）を継承。位置情報は Preferences で可否 |
| auto-export | 撮影完了ごとにバックグラウンドで書き出し、`PHPhotoLibrary` に保存 |
| HDR 書き出し | v3。ISO 21496-1 ゲインマップ付き HEIC。シーンリニアを持っているので原理的に容易 |

### 7.4 アーカイブ

- 選択した写真の `<uuid>/` ディレクトリ（`cache/` を除く）を zip にまとめ、Files アプリへ書き出す。使用している各 `lookVersion` の `Looks/<lookVersion>/look.json` も同梱し、アーカイブ単体でパラメータが分かるようにする。
- インポートは zip を展開してライブラリに追加する。`lookVersion` の扱い:
  - アプリが同じ `lookVersion` と `pipelineVersion` を持つ → 同一として表示。
  - `lookVersion` は未知だが、同梱の `look.json` が示す `pipelineVersion` をアプリが持つ → 同梱パラメータで表示し、同一として扱う。
  - `pipelineVersion` も未知 → 最も近い `pipelineVersion` で近似表示し、「当時と同じ画ではない」と警告する。黙って最新ルックに置き換えない。
- `decoder.usedVersion` が移行先の端末で使えない場合も同様に近似扱いとする。

再現性の検証（受け入れ条件）

| 検証 | 方法 | 判定 |
|---|---|---|
| アーカイブ往復 | 端末 A で書き出し → 端末 B（同 OS、同デコーダー）で取り込み → レンダリング | `render.json` のハッシュと一致（ビット一致）。デコーダーが異なる場合は ΔE2000 平均 < 0.5 |
| ルック更新後の再表示 | 新しい `lookVersion` を追加したアプリで、旧 `lookVersion` の写真を再レンダリング | 旧 `render.json` のハッシュと一致 |
| キャッシュ削除後の再合成 | `cache/` を削除して再合成 | 以前の `merged.exr` とリニア値の最大絶対差 < 1e-3 |
| 未知バージョンの取り込み | `pipelineVersion` が未知のアーカイブを取り込む | 近似表示と警告が出て、「同一」と表示されない |

## 8. ライブプレビューについての方針

本家は「撮影後にギャラリーで見る」設計を採っている。技術的な理由と思想的な理由の両方がある。

- 技術: 12MP Bayer のデモザイクとルック適用を 30fps で回すのは A17 クラスでも厳しく、電池を食う。
- 思想: プレビュー YUV に LUT を当てる「近似プレビュー」は Apple の処理の上にフィルターを乗せることになり、「フィルターではない」という主張と矛盾する。ユーザーがプレビューと仕上がりの差に混乱する。

本仕様の方針
- **v1: プレビューにルックを当てない。** 本家と同じ。
- **v3 で検討: 「参考プレビュー」を明示的なオプションとして提供。** プレビュー YUV を sRGB → 逆トーンマップで擬似リニアに戻し、3D LUT を当てる。精度は低いことを UI に明記する。本家が最も批判されている点なので、クローンの差別化要素になりうる。ただし既定はオフ。

## 9. ルック開発の進め方（アプリとは別のツールチェーン）

ルックの数値はアプリの中で決めるものではない。先にオフラインで作り、アプリは「再生装置」にする。

1. **参照画像の収集**: 自分の iPhone で DNG を 100 枚程度撮る。人肌、空、緑、夕景、室内タングステン、ネオン、白いもの、黒いもの。
2. **Python での試作**: `rawpy`（LibRaw）で DNG をリニア化し、`numpy` と `colour-science` で [B]〜[G] を実装。Jupyter で参照画像を並べながらパラメータを追い込む。
3. **目標の設定**: 製品目標は独自ルック（§5.0）。Yedlin の公開手法は実測データへの合わせ込みだが、本プロジェクトではフィルムの実測は行わず、「好きな写真」を数枚選び、それに近づける。本家への近似を目標に加える場合は、撮り比べの比較画像と評価方法（ΔE2000、目視 A/B）を先に定義し、別マイルストーンにする。
4. **3D LUT への焼成**: 決まったパラメータから `.cube`（65³）とパラメータ JSON を出力。
5. **アプリへの組み込み**: Metal 側は同じ数式を Swift/MSL で実装し、Python 側と同一入力で出力一致をテストする（許容誤差 1/1024）。テストは §5.2 の期待値表、§6.2 の同一ノイズ比較、段構成の順序（LUT-A → [F] → [G]）を含む。定数は `shaper.json` と `look.json` を両側で読み込み、別々に書かない。つまみ操作時はアプリ内で LUT-A を再焼成。

この分離により、ルックの改良はアプリのリリースと独立に行える。

## 12. 本家に対して改善できる点（クローンの差別化）

本家のレビューや報道で挙がった不満のうち、設計を崩さずに対応できるもの。**本家に該当機能が無いことは、公式記述がない限り未確認（利用者報告、バージョン不明）である**（レビュー指摘 #12）。ここでの「対応」は本アプリの実装方針であり、本家との差別化が成立するかは、対象バージョン・確認日・操作手順を記録した上で別途確認する。確認するまで差別化として確約しない。

| 本家への不満（確度） | 対応（本アプリの実装方針） | 設計との整合 / 差別化の扱い |
|---|---|---|
| 撮影時にルックが見えない（公式: 仕様として明記） | 参考プレビュー（既定オフ、精度の低さを明記） | 本流パイプラインとは別と明示すれば矛盾しない。差別化として扱える |
| シャープニングがない（利用者報告、複数） | デモザイク直後に控えめなデコンボリューション（Apple 的なエッジ強調ではなく、レンズのボケを戻す方向）をオプションで | シーンリニア段で行えば「フィルター」ではない |
| 48MP 不可（利用者報告） | §2.5 の実機確認の結果次第。Bayer RAW で取得できなければ ProRAW ベースの別モードとしてのみ提供可能で、その場合「別プロセス」ではないと明示する | 差別化として確約しない |
| ハレーション量を調整できない（**未確認**。報道は調整可能、利用者報告は不可で食い違う） | つまみを提供する。本家の状況に関わらず実装する | [A] のゲインを露出するだけ。差別化とは主張しない |
| 編集時にモノクロへ切替できない（利用者報告、バージョン不明） | RAW はカラーなので可能 | [D] の切替。差別化は未確認 |
| WB 固定できない（利用者報告、バージョン不明） | 撮影時の WB ロックと、編集時の数値指定 | [A]。差別化は未確認 |
| 英語のみ（App Store の記載） | 日本語対応 | 差別化として扱える |

## 13. 技術的リスク

| リスク | 影響 | 対策 |
|---|---|---|
| CIRAWFilter で無効化できない処理が残る（RAW 9 の CoreML 色ノイズ処理など） | Apple の処理が混ざる。OS 更新で見た目が変わる | `decoderVersion` を固定し、§3.1 の対応表と検証で「切れる処理」「残る処理」を明記する。根本対策は v2 の自前デモザイク |
| デコーダーの固定版が将来の OS で使えなくなる | 過去の写真を「同一」で再現できない | 近いバージョンで近似表示し、UI に明示（§3.1、§7.1）。自前デモザイクで解消 |
| Bayer RAW 非対応機種 | 旧機種で動かない | 起動時に判定し、非対応なら明示。ProRAW へのフォールバックは「別プロセス」でなくなるので行わない |
| ブラケットのゴースト | 動体で破綻 | 静止判定で単発に落とす。合成後の残差マップを保存し、将来の改良に使う |
| ルックが「好み」に収束しない | 製品の核が定まらない | M0 に時間を割く。アプリ実装より先にルックを決める |
| Bayer RAW が 12MP に制限される | 高解像度 Bayer モードが成立しない | §2.5 の実機確認で判定。ProRAW は別前提のモードとして扱い、「別プロセス」とは呼ばない |
| 48MP でメモリ不足 | クラッシュ | タイル処理。v1 では 12MP 固定 |
| 本家の機能を「無い」と誤認して差別化を誤る | 優先順位と訴求を誤る | 未確認事項は §12 の確度欄で区別し、確認記録を残してから差別化と呼ぶ |
| Core Image と Metal の往復コスト | 性能 | `CIRenderDestination` で直接 MTLTexture に描き、往復を 1 回に抑える |
